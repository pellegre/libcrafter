## Reviewed Facts

| Requirement area | Source-backed fact | Evidence | Implementation note |
| --- | --- | --- | --- |
| Packet model | mDNS uses DNS-like UDP query and response messages, existing DNS message structure, name syntax, resource record types, and no new opcodes or response codes. DNS-SD likewise changes no DNS message structure, opcodes, rcodes, RR types, or other DNS protocol values. | RFC 6762 Sections 1, 2, and 18; RFC 6763 Introduction. | Keep mDNS inside `Dns`/`Packet`; do not add a resolver, daemon, cache, scanner, or separate packet surface. |
| UDP endpoint | mDNS uses UDP port 5353. Compliant queriers send from UDP source port 5353 and listen for replies to destination port 5353. Responses use source port 5353 and destination port 5353 except for permitted unicast response cases. | RFC 6762 Sections 2, 5, 5.5, 6, 18, and 22. | Add default helpers for 5353 while allowing caller overrides for malformed or legacy packet construction. |
| Multicast IP destinations | `.local.` queries use IPv4 link-local multicast `224.0.0.251` or IPv6 `FF02::FB`; responses normally target those addresses except explicitly requested unicast/legacy/direct-unicast cases. IANA allocated UDP 5353, IPv4 `224.0.0.251`, and IPv6 `FF0X::FB`; deployed use is `FF02::FB`. | RFC 6762 Sections 3, 5, 6, 11, 12, and 22. | IPv4 and IPv6 multicast destination constants are source-backed. Wider-scope IPv6 mDNS is not a default; make scope explicit if exposed. |
| Ethernet multicast destinations | IPv4 multicast-to-Ethernet mapping uses `01:00:5e` plus low-order 23 bits, yielding `01:00:5e:00:00:fb` for `224.0.0.251`. IPv6 multicast-to-Ethernet mapping uses `33:33` plus the low-order 32 bits, yielding `33:33:00:00:00:fb` for `ff02::fb`. | RFC 1112 Section 6.4; RFC 2464 Section 7. | These are derived link-layer constants, not mDNS-specific allocations. Keep derivation documented near any Ethernet helper. |
| Hop-limit/IP TTL | Multicast DNS responses, including unicast responses, SHOULD be sent with IP TTL/hop limit 255. The reviewed RFC evidence does not state a query TTL default in the same normative form. | RFC 6762 Section 11. | Default response helpers may use 255. Do not claim a sourced query TTL default from this note; expose any query TTL helper as a conventional default with override. |
| Header defaults | Multicast query ID SHOULD be zero; multicast response ID MUST be zero and ignored on receipt. Query QR is 0, response QR is 1. Multicast OPCODE is 0. Query AA is 0; multicast-domain responses set AA to 1. RD SHOULD be 0; RA/Z/AD/CD/RCODE MUST be 0; nonzero OPCODE/RCODE messages are ignored by compliant mDNS. | RFC 6762 Sections 18.1-18.11. | Builders should default these values but not prevent explicit caller overrides where existing DNS encoding permits them. |
| QU question bit | The top bit of qclass in a question is the unicast-response-preferred bit. Set means the querier accepts unicast replies for that question; lower 15 bits remain the DNS class. | RFC 6762 Sections 5.4 and 18.12. | Provide helpers that mask `0x8000` without corrupting the raw qclass. |
| Cache-flush RR bit | The top bit of rrclass in Resource Record Sections of mDNS responses is the cache-flush bit for unique RRSets. It is not part of the DNS class; actual class is the lower 15 bits. It must not be set in query known-answer records or shared records, and not in legacy unicast responses to non-5353 ports. | RFC 6762 Sections 8.3, 10.2, and 18.13. | Provide raw-class preserving helpers for `0x8000`; summaries should show both base class and cache-flush state. |
| Query/response sections | mDNS responses must not contain questions; received questions in responses are ignored. Queries may contain known answers in the Answer Section and probe tiebreak records in the Authority Section. | RFC 6762 Sections 6, 7.1, 8.2, and 18.14. | Packet builders may create these shapes; no persistent responder behavior belongs in the crate. |
| Known-answer behavior | A querier lists known answers in the query Answer Section. A responder suppresses an answer if the listed RR TTL is at least half the true TTL; if less than half, it answers. Multipacket known-answer lists use TC in the query to signal more known answers. | RFC 6762 Sections 7.1 and 7.2. | Implement packet helpers for known-answer sections and TC flag shape only; no cache implementation. |
| Probing | For unique records, probes use the desired name/class, usually IN, and qtype ANY. Probes are sent three times at 250 ms intervals after an initial random delay; probe packets SHOULD be QU. Simultaneous probe tiebreaking uses proposed records in the Authority Section and compares class without cache-flush, then type, then raw rdata. | RFC 6762 Sections 8.1 and 8.2. | Crate helpers can build probe packets and expose tiebreak-comparable bytes; timing/conflict state stays in generated tools or probes. |
| Announcements | After probing, a responder sends unsolicited mDNS responses with newly registered records in the Answer Section. Shared records are placed as-is; unique records set cache-flush. At least two unsolicited responses are sent one second apart. | RFC 6762 Section 8.3. | Provide announcement packet builders only. Scheduling stays outside `crafter`. |
| Goodbyes | When RR data is about to become invalid, a host SHOULD send an unsolicited response with same name/type/class/rdata and RR TTL zero. Receivers record TTL 1 and delete one second later. | RFC 6762 Section 10.1. | Packet helper can set TTL zero; cache deletion semantics are peer behavior, not crate state. |
| DNS-SD browse | Browsing queries PTR at `<Service>.<Domain>` and receives zero or more PTR records to `<Instance>.<Service>.<Domain>`. Service type enumeration uses PTR name `_services._dns-sd._udp.<Domain>` and PTR rdata of two-label service names such as `_http._tcp.<Domain>`. | RFC 6763 Sections 4.1 and 9. | Name helpers should build browse names and service-enumeration names without changing DNS wire format. |
| DNS-SD resolve | Resolving a selected service instance queries SRV and TXT at the Service Instance Name. SRV gives target host and port; TXT gives structured extra data. A single advertised DNS-SD instance is commonly represented by one SRV record with priority and weight set to zero. | RFC 6763 Sections 5 and 6. | Bonjour-style resolve helpers should emit PTR/SRV/TXT plus address additionals, not perform connection logic. |
| DNS-SD additionals | A PTR response SHOULD include the SRV record(s), TXT record(s), and A/AAAA records named by SRV rdata. An SRV response SHOULD include A/AAAA records named by SRV rdata. TXT responses add no additional records. | RFC 6763 Sections 12.1-12.3. | Record-set helpers can include additionals for deterministic Bonjour-like packets. |
| Service instance labels | The instance label is arbitrary Net-Unicode text, excluding ASCII control bytes, stored as a single UTF-8 DNS label, with DNS label length limits. Literal dots and backslashes need escaping when a string form concatenates instance, service, and domain. | RFC 6763 Sections 4.1.1 and 4.3. | Support escaped dots/backslashes and UTF-8. Non-text bytes are not DNS-SD instance-label behavior from RFC 6763; preserve them only as raw DNS names where the existing DNS layer permits. |
| Service names and subtypes | The service portion is two labels: `_<Service>` plus `_tcp` or `_udp`. Subtype browse names use `<Subtype>._sub.<Service>.<Domain>` and PTR to the same service instance name; the subtype does not change the SRV/TXT owner name. | RFC 6763 Sections 4.1.2 and 7.1. | DNS-SD helpers should keep subtype PTR names separate from service instance owner names. |
| TXT records | Every DNS-SD service has a TXT record with the same name as SRV, even if it is a single zero byte. TXT rdata is one or more strings, each length byte plus 0-255 bytes. DNS-SD strings are `key=value`; unknown keys are ignored; SRV target host and port must not be duplicated in TXT. | RFC 6763 Sections 6, 6.1, 6.2, 6.3, and 6.4. | Preserve TXT bytes exactly; optional structured views must not reject unknown keys or unusual values. |
| RR/class codepoints | IANA DNS Parameters selected in the manifest confirm DNS CLASS IN=`1`, QCLASS ANY=`255`, RR TYPE A=`1`, PTR=`12`, TXT=`16`, AAAA=`28`, SRV=`33`, and ANY=`255`. | IANA DNS Parameters registries `dns-parameters-2` and `dns-parameters-4`; RFC 1035; RFC 2782; RFC 3596. | These constants are safe for mDNS/DNS-SD helpers. Unknown RR types still round trip as raw data. |

The generated manifest does not include Apple source content, so Bonjour compatibility claims beyond RFC 6763 packet shapes remain unsupported here. | RFC 6763 Sections 7.1, 18.2, and Appendix G. | Build Bonjour-like packet shapes from DNS-SD RFC evidence; do not add Apple-specific behavior without a later Apple source review. |
